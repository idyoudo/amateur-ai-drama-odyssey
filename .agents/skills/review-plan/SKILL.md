# Review Plan（AADO）

只读审计。默认不改代码、不更新计划、不 commit/push；用户明确要求修复时才动手。输出简体中文，问题优先。

## 先分级，再审计

- **快速核对**：单点文档/文案/常量/局部 bug，不涉及新功能点、数据模型、契约、权限、迁移。
- **标准审计**：多文件协作、需确认调用链/数据流、或快速核对无法证明结果。
- **完整审计**：新增模块/功能点、改数据模型/API/契约、权限、跨模块、数据完整性，或用户点名完整 review。

## 强规则对照（任何档位都做）

- 改 `PRD/` 的改动，三处台账（CHANGELOG.md / changelog.jsonl / 文件内变更记录）是否齐备（强规则一）。
- 触及 `M#` 模块的改动，`docs/modules/M#-*.md` 的 §2 是否登记、§4 是否回写（强规则三）。**缺登记/未回写 = `Important`**。
- 结论是否来自实际代码/diff/命令输出/可复现运行；没有证据标「未验证」。**声称机器验证却拿不出命令与数字 = `Important`**。

## 证据纪律

1. 结论必须来自实际代码、diff、命令输出或可重复运行；无证据标「未验证」。
2. 区分本次改动与工作区无关修改，别把无关未提交文件当当前问题。
3. 快/轻没有 `docs/plans`/`docs/spec` **不是缺陷**；但**缺机器验证证据（三条命令未跑/跑红）是缺陷**。

## 问题分级

- `Critical`：数据/证据链损坏、破坏门禁、关键功能不可用、完整档核心目标未完成。
- `Important`：明显范围膨胀、缺必要验证、破坏架构边界、强规则登记缺失、重要边界 bug。
- `Minor`：可维护性、命名、低风险一致性。
- `Question`：证据不足，需确认。

不要把风格偏好当问题。

## 输出格式

```markdown
## 审计结论
[通过 | 有条件通过 | 不建议继续]：1–3 句

## 发现的问题
- `Critical` `path:行号`：…；建议修复方向。

## 未验证或证据不足
- …

## 对照
- 已完成 / 未完成 / 计划外

## 建议下一步
1. …
```

无阻塞问题写「未发现阻塞性问题」，仍列出未跑验证与剩余风险。
