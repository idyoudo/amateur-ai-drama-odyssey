# PRD 目录 · Amateur AI Drama Odyssey

**项目名称**：Amateur AI Drama Odyssey（代号 `amateur-ai-drama-odyssey`，缩写 **AADO**）—— 一套「好莱坞级 AI 短剧」产品。
**宿主平台**：Retail Trading Odyssey（RTO）。本项目当前实现在 RTO 仓库内，下文中出现的「RTO」均指**宿主平台/现有实现**，不是本项目名。
**本目录**：上述项目的 PRD 唯一归档位置，长期维护、逐版累积。

PRD 回答的是「**为什么做、给谁做、做什么、做到什么程度算完成**」，是需求本身，不是实现方案。

## 一、本目录只放 PRD

**属于本目录**

- 项目背景与整体链路说明（L1）
- 项目模块与子模块的需求定义（L2 / L3 / L4）
- 具体功能点及其验收标准
- 需求评审结论、范围变更、搁置原因

**不属于本目录**（请放到对应位置，不要混进 PRD）

| 内容 | 该放哪里 |
|------|----------|
| 开发计划、任务拆分、改动点清单 | `docs/plans/` |
| 执行记录、验证证据 | `docs/spec/` |
| 技术设计、架构说明、方案选型、表结构、接口设计 | `docs/architecture.md`、`docs/plans/`、代码模块文档 |
| 部署、运维、使用指南 | `docs/guid/` |

一句话：**PRD 里不写「怎么实现」，只写「要什么、为什么、怎样算达标」。**

## 二、PRD 分层规则（L1 → L2 → L3 → L4 → 功能点）

整份 PRD 是一棵树：**项目背景 → 项目模块 → 二级模块 →（按需三级、四级）→ 具体功能点**。

| 层级 | 名称 | 说明 | 示例 | 落位方式 |
|------|------|------|------|----------|
| **L1** | 项目（模板） | 整个短剧项目的背景、目标用户、端到端链路、范围与非目标 | 「自动生成 AI 短剧」项目总览 | 一个文件：`00-项目背景.md` |
| **L2** | 项目模块 | 项目的一级能力域，互不重叠、合起来覆盖完整链路 | 剧本生成、素材生成、配音与字幕、成片合成、任务编排、项目管理 | **一个模块一个文件** |
| **L3** | 二级模块 | 模块内的子能力 | 「素材生成」下的：文生图、图生视频、素材上传 | 所属 L2 文件内的一级章节 |
| **L4** | 三级模块 | 继续细分，按实际需要决定是否存在 | 「图生视频」下的：首帧处理、供应商与模型选择 | 所属 L3 章节内的小节 |
| **FP** | 功能点 | 可验收的最小需求单元，PRD 的叶子节点 | 「支持选择视频供应商与模型」 | 所属章节内的功能点条目 |

分层规则：

1. **按需分层，不强行凑齐**：L3、L4 只在确有细分必要时才出现；功能点也可以直接挂在 L2 下。
2. **不允许跳级**：出现 L3 就必须先有它所属的 L2；出现 L4 就必须先有 L3。
3. **模块划分必须满足 MECE**：同一功能点只能出现在一个模块下，不重复登记。
4. **一个模块文件不超过约 30 个功能点**；超出则拆分子模块章节或独立文件，避免文件失控。

## 三、编号规则

全目录统一编号，正文、索引、提交信息、计划文档引用同一套编号。

```text
模块      M1、M2、M3 …            L2
子模块    M1.1、M1.2 …            L3
细分模块  M1.1.1、M1.1.2 …        L4
功能点    M1.1.1-F01 …            FP
```

- 编号一经分配**不再复用**：模块废弃时保留编号并标记 `已废弃`，新模块顺延取号。
- 跨文档引用只写编号（如 `M3.2-F04`），不写文件路径，避免路径变动导致引用失效。

## 四、功能点的必填字段

**盘点阶段**（状态为 `规划中` / `待评审`）允许先用功能点清单表登记：`编号 | 功能点 | 能力与规则 | 状态 | 证据`；**进入 `已确认` 前**必须按下方字段补齐用户故事、边界与异常、验收标准。

本 PRD 是**目标态**产品文档：既要写清「现在有什么」，也要写清「要做到什么」。因此每个功能点分两栏描述：

- **现状**：当前系统的事实（有代码证据的写 `file:line`，没有的写「未实现」）。
- **目标态**：产品要达到的最终形态（含新增能力、要补齐的缺口、要提升的质量）。

每个功能点都必须写全下列字段，缺字段视为未完成：

| 字段 | 说明 |
|------|------|
| 编号 | 如 `M2.3-F01` |
| 名称 | 一句话说清能力 |
| 用户故事 | 作为〈某类用户〉，我希望〈做什么〉，以便〈获得什么价值〉 |
| 输入 / 输出 | 用户或系统提供什么，产出什么（业务语言，不写字段类型） |
| 交互与规则 | 关键操作路径、默认行为、约束 |
| 边界与异常 | 空数据、失败、无权限、超时、重复提交等如何处理 |
| **验收指标** | 可二值判定或可量化（阈值 + 测量方式），例：「单集重复付费调用 = 0 次」「人脸相似度 ≥ 0.6」 |
| 依赖 | 依赖的功能点编号或外部能力 |
| 优先级 | P0 必须 / P1 重要 / P2 可选 |
| 状态 | 见下节取值 |
| 证据 | `已实现` 给代码 `file:line`；`规划中` 给**业界依据**（对标产品、论文、公开实践 URL）；都没有则标 `待核实` |

### 4.1 业界依据的写法

新增（`规划中`）能力不能凭空设计，必须有依据，三选一：

1. **对标**：某成熟产品已有的同类能力（写产品名 + 版本/时间 + URL）；
2. **论文/标准**：如 VBench 指标、深度合成标识办法（写标准名 + URL）；
3. **本项目实测**：写明数据来源与采集时间。

依据统一登记在 [99-业界对标与调研.md](99-业界对标与调研.md)，功能点里只写编号引用（如 `依据：A-12`）。

**两种写法都合规**：

1. **内联**：写在功能点的「目标态与规则」列里——**改变产品形态的关键能力必须内联**；
2. **模块级**：写在所属模块的「## 目标态依据（模块级）」小节，按功能簇登记，本模块 `规划中` 功能点继承该依据。

评审时先看模块级依据是否覆盖本模块全部 `规划中` 功能簇，再抽查关键能力是否内联。

## 五、状态与证据规则

状态取值（全目录统一）：

`规划中` / `待评审` / `已确认` / `开发中` / `已实现` / `已上线` / `已废弃`

- **规划中**：目标态已定义，但代码尚未实现（含当前完全缺失的能力）。
- **已实现 vs 已上线**：代码完成标 `已实现`；经远端部署验收后标 `已上线`。
- **证据必须有**：`已实现` / `已上线` 的功能点必须给出代码或执行记录证据（`file:line`、`docs/spec/...`）。
- **找不到证据**：标 `待核实`，不要凭文档描述臆断为已实现。
- **代码与 PRD 冲突**：以代码事实为准，并立即修正 PRD，同时在变更记录里写明。

### 5.1 非功能需求（NFR）单独成章

可靠性、成本、性能、质量、安全合规等**不写成普通功能点**，统一写在 L1 项目总览的「非功能需求」章节，每条必须包含：

| 字段 | 说明 |
|------|------|
| 指标 | 例如「单位成片成本」「断点续跑成功率」「单集产出时长」 |
| 目标值 | 可量化阈值（如 ≤ ¥8 / 分钟成片） |
| 测量方式 | 数据从哪里来、怎么算 |
| 兜底策略 | 超限时的行为（熔断、降级、转人工） |

### 5.2 模块内的功能点按「用户旅程顺序」排列

同一模块内，L3 二级模块按用户在真实制作流程中的先后顺序排列，便于评审时按流程走查。
