## 三、编排可靠性与成本治理（E 系列）

调研时点：2026-10-11。**证据限制**：本轮 `web_fetch` 对全部域名失败（解析到非公网 IP），页面正文未读到，证据仅来自 `web_search` 的标题与片段；凡具体倍率/阈值/默认值一律标注 **未核验**，不得作为指标承诺。

### 3.1 编排引擎结论

| 编号 | 结论 | 依据（官档 URL） |
|------|------|------------------|
| E-01 | **不必更换现有架构**：RTO 的「PG 单表 SKIP LOCKED + 心跳租约 + 幂等键 + 阶段闸门 + 断点续跑」已属「自研耐久执行内核」，与 DBOS / Hatchet / River / Oban 同一路线；缺的是**调用级幂等、不确定态对账、fencing** 三件事 | https://www.dbos.dev/blog/postgres-is-all-you-need-for-durable-execution 、https://riverqueue.com/docs/unique-jobs 、https://hexdocs.pm/oban/0.8.1/Oban.Job.html |
| E-02 | 若要替换引擎，候选优先级：**Hatchet**（PG 基座、迁移最省）> DBOS（库级嵌入）> Restate（异步回调/HITL 最优）> Temporal（能力最全、运维最重） | https://docs.hatchet.run/v1/durable-tasks 、https://docs.restate.dev/ai/patterns/human-in-the-loop 、https://docs.temporal.io/ai/cookbook/human-in-the-loop-python |
| E-03 | **不要**用 Airflow/Dagster/Prefect/Argo 承担「付费调用去重」——它们是调度器，不是单次外部调用的事务边界；但 Dagster 的「资产物化 + 只重跑受影响子图」语义值得抄 | https://docs.dagster.io/guides/build/assets/modeling-etl-pipelines |

### 3.2 幂等与去重（P0）

| 编号 | 实践 | 要点 | 依据 |
|------|------|------|------|
| E-04 | **请求指纹** | `sha256(provider \| model \| prompt \| params \| seed \| 输入资产 hash)`，DB 唯一索引；**模型升级必须换指纹**，否则新旧产物混用 | https://riverqueue.com/docs/unique-jobs |
| E-05 | **幂等键范式** | 客户端生成 key，服务端在同一 key 下返回首次结果而非重复执行 | https://docs.stripe.com/api/idempotent_requests |
| E-06 | **供应商无幂等键的兜底** | 按「供应商无幂等键」设计：**查单对账 + 时间窗指纹抑制 + 人工核对队列** | https://docs.volcengine.com/docs/ark/list-video-generation-tasks-api?lang=zh 、https://www.alibabacloud.com/help/tc/model-studio/manage-asynchronous-tasks |
| E-07 | **回调幂等** | webhook 会重复投递，按 prediction/task id 幂等 UPSERT | https://replicate.com/docs/topics/webhooks/receive-webhook |
| E-08 | **intent log** | 调用前先写 `intent(project, shot, fingerprint, client_op_id, status=submitted)`；超时置 `unknown`，**禁止直接重发** | 社区范式，与 E-05 同源 |

### 3.3 租约、fencing 与回收（P0）

| 编号 | 实践 | 要点 | 依据 |
|------|------|------|------|
| E-09 | **租约 + fencing token** | 领取时发放单调递增 `lease_epoch`，**所有产物写入校验 epoch**；对象存储用「临时路径 + 校验 epoch 后原子改名」 | https://pages.cs.wisc.edu/~remzi/Classes/739/Spring2003/Papers/leases-redis-problem.pdf |
| E-10 | **可见性超时等价物** | SQS visibility timeout 是业界标准语义：领取后不可见，超时未删则重新可见（即 RTO 心跳续租） | https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html |
| E-11 | **队列表卫生** | 领取+更新必须短事务（避免阻碍 vacuum）；单集互斥用 advisory lock；队列表定期归档 | https://www.postgresql.org/docs/current/sql-select.html |

### 3.4 重试经济学（P0）

| 编号 | 实践 | 要点 | 依据 |
|------|------|------|------|
| E-12 | **指数退避 + 全抖动** | `min(cap, base·2^n)·random`，尊重供应商 `Retry-After`；无 jitter 会形成重试风暴 | AWS Well-Architected（本轮仅命中本地化 PDF，**原文 URL 未核验**） |
| E-13 | **重试预算** | 全局「重试数/总请求数」上限，超限**拒绝重试并降级** | https://grpc.io/docs/guides/retry/ 、https://www.envoyproxy.io/docs/envoy/v1.35.9/configuration/upstream/cluster_manager/cluster_circuit_breakers |
| E-14 | **分层 attempt_limit** | 按阶段配置重试上限（当前全局 2 偏粗）；内容类错误不重试，网络类可重试 | RTO 现状 + E-13 |
| E-15 | **失败样本复用 + 死信队列** | 重试复用前置成功产物，避免「重试 = 从头再来」 | 社区模式 |
| E-16 | **重复付费计数器** | 独立校验器比对指纹库与供应商账单/请求日志，把「重复付费调用」做成硬指标 | E-05、E-06 |

### 6.3 成本与工程结论（E/F 系列）

| 编号 | 结论 | 要点 | 等级 |
|------|------|------|------|
| E-30 | **TTS 不是成本瓶颈，口型才是** | 一集 1500 汉字 TTS 约 0.24–0.45 元；口型 1 分钟 **$1.2–8**，是 TTS 的 **10–50 倍** → 口型必须有「只做近景正脸」的策略与失败降级 | 官档定价换算 |

| F-14 | TTS 单价（阿里，按汉字计 2 字符） | 1 万汉字 ≈ **1.6 元**（qwen3-tts-flash）/ **3 元**（cosyvoice-v3.5-plus） | 官档 |

### 7.3 工程结论（E/F 系列）
